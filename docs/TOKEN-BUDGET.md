# 上下文预算

本文说明当前代理的预算规则，并记录上游补测结果。输入与输出共享模型的上下文窗口，`config.js` 中的模型配置给出参数预算上限，实际生成长度还取决于上游服务。

图片预算先读取 data URL 中有限的文件头取得宽高，再按模型公式估算 token。图片估值只辅助调整客户端指定的输出上限，实际图片用量取上游返回的 `usage`，估值不会单独触发本地 413。

## 当前规则

本地预算用于适配客户端过大的输出参数。

- 用随包分发的 DeepSeek 词表估算文本，计入历史思考和工具字段。
- 在本地计数之外，预留 1,024 token，以及每项工具定义 20 token 的模板余量。
- Qwen 额外预留本地输入估算的 20%，补偿不同词表与模板造成的偏差。
- 支持范围内的静态 PNG/JPEG/WebP 按尺寸与公开模型处理器规则估算图片 token，每图另留 8 token 软余量。需要回退的图片按每张 16,384 token 软估计，不再另加 8 token。标准图片字段中的 Base64 不当作文本计数。

接近窗口上限时，代理先按文本、工具与模板余量收缩显式指定的输出预算；需要收缩却无法容纳最低输出（思考开启 512，关闭 1 token）时，返回 413。未指定 `max_tokens` 时不注入默认值，仅在文本估算与上述余量超过窗口时拒绝。

图片估值和图片余量不计入本地拒绝请求的硬余量。扣除图片预算后仍能容纳最低输出时，进一步收缩显式输出上限；若不足，则保留按文本适配后的上限，交由上游判断，不因此返回 413，也不强行把输出压到最低值。图片估算不依赖历史请求，不做图片哈希或用量学习缓存。

上游明确返回的 HTTP 400 上下文超限保留为 400，并提供 `context_length_exceeded` 错误码；其他 HTTP 400 请求错误也保留为 400。上游 HTTP 413、429 仍按原有规则处理。客户端是否据此自动压缩会话取决于客户端实现；上游拒绝时，可缩短对话、减少历史图片或降低输出上限。

本地请求体大小限制独立于 token 预算，默认 64 MiB，包括 JSON 和 Base64 图片。图片预算的处理方式不会改变这项限制。

日常日志保留请求结果、耗时与上游实际 token 用量。预算检查和输出收缩始终执行；需要排障时，在启动前设置 `PROXY_DEBUG_BUDGET=1`，查看文本估算、模板与工具余量、图片估值与余量、输出预算和上下文窗口。

## 模型窗口与传输限制（2026-10-17）

本次配置更新依据维护者提供的三层探测报告（本机 v1.10.6 代理、前端 bundle、使用本机凭据直连上游）。以下数值描述请求参数校验，不代表模型实际生成了这么多 token。

- **R1**。上游报错明确给出 163,840 token 的共享窗口；短输入下 `max_tokens: 160000` 成功，8 token 输入加 163,832 输出被拒绝。163,832 是该请求的拒绝点，不能作为独立输出上限。配置的 `maxOutputTokens: 163840` 表示共享窗口预算天花板，请求仍会扣除本地输入估算与至少 1,024 token 余量。
- **Qwen**。SSE 请求接受 `max_tokens: 262000`；相同参数改为非流式，报错 `Range of max_tokens should be [1, 131072]`。代理向上游统一请求 SSE，非流式客户端由代理聚合，因此沿用 262,000 预算。未指定预算时不注入上限。
- **DeepSeek V4.1**。共享窗口与输出预算仍为 1,048,576，实际可用输出需扣除输入与余量。

同日追加短请求复核，Qwen 的 `auto`、`required` 和指定工具均返回原生 `tool_calls`，因此取消旧的 `tool_choice: none` 降级。指定工具时，直连上游 SSE 与非流式响应都出现了完整调用配 `finish_reason: "stop"` 的情况；代理仅在调用校验通过后将 `stop` 统一为 `tool_calls`。修复后的 5 次 Qwen 验证均由一次上游原生响应完成，覆盖 `auto`、指定工具的流式与非流式客户端，以及 `required` 流式客户端。

发版审阅时又用 `Reply only OK.` 短输入发送 5 次预算探测，复核上述边界。R1 在 `max_tokens: 163840` 时明确报告窗口为 163,840、输入为 9 token；实际传输状态为 HTTP 200，正文为 `BadRequestError` 且 `error.code: 400`。`max_tokens: 160000` 已进入 SSE 生成，为控制配额，在收到超过 4,096 个字符后主动中止，仅据此确认参数被接受。Qwen 的流式 262,000 与非流式 131,072 均正常完成，各返回 16 输入、2 输出 token；非流式 262,000 返回 HTTP 400，并明确给出 `[1, 131072]` 范围。代理兼容 HTTP 200 中的明确 400 错误，避免将这种上下文超限误报为 502。

## 图片尺寸估算

本地只将 Base64 的开头一段还原成最多 64 KiB 的二进制头部，读取 PNG 的 IHDR、JPEG 的 SOF 或 WebP 的尺寸字段，并检查所读范围内的格式与动画标记。这里不解压图片像素、不缩放或修改原图，也不下载远程 URL。运行时不为估算额外调用上游，不维护图片哈希或用量学习缓存。

目前尺寸公式只匹配请求中的 `DeepSeek-V4.1-Flash` 和 `qwen3.8-27b` 两个模型 ID。静态 PNG/JPEG/WebP 通过头部检查、每边不超过 8192 像素且长宽比不超过 8 时，使用对应模型的公式。`detail` 未指定或为 `auto`、`low`、`high` 时使用相同规则。

远程图片 URL、GIF、APNG、动画 WebP、无法识别或不完整的头部、超出上述尺寸范围、未知模型 ID 或不支持的 `detail` 值，均回退到每图 16,384 token。该值仅用于软预算；输出空间不足时仍按前述规则交给上游判断。

JPEG 的 EXIF 方向 5–8 会交换逻辑宽高。PNG 在首个 IDAT 前发现 `eXIf`，以及 WebP 声明 EXIF 或在所读头部中发现 EXIF 块时，使用未知回退；当前并未完整解析所有格式、所有位置的 EXIF。头部之外的损坏也不在本地校验范围内。

- **DeepSeek-V4.1-Flash**。按公开处理器先将不足 295,936（544²）像素的图片等比放大，逐边截断为整数，再向上对齐 14 像素 patch。3 倍下采样得到 token 网格 `rows × columns`，计数为 `rows × (columns + 1) + 2`，包含每行换行和图片起止标记。若超过 1024 token，按官方 `solve_resize_ratio` 求缩放比例并向下对齐 patch；不能用固定最大像素面积替代这一步。
- **qwen3.8-27b**。按公开 `smart_resize` 将每边舍入到 32 的倍数，恰好半格时取偶数。用舍入后的面积检查 65,536 至 16,777,216 像素范围，超出时按原始面积等比缩放，缩小时逐边向下对齐，放大时向上对齐。中心计数为 `(resize宽 / 32) × (resize高 / 32) + 2`，包含图片起止标记。实现保留上游浮点运算顺序，例如 239² 会得到 81 个视觉占位 token，而非 64 个。

两模型均在中心计数之外另留每图 8 token 软余量，`detail: auto/low/high` 使用相同规则。当前实测没有发现 `low` 降低图片计数。模型托管服务未公开后端提交版本；公开算法与当前样本一致，不保证服务更新后仍一致，因此图片计数和余量都不参与本地硬拒绝。

发布前新增 112 次 API 请求均成功，其中 31 次先记录预测再发送请求的独立验证全部匹配。连同历史，155 条用于公式回归的含图记录全部匹配，去重后为发布时的 128 条观测。发布后又补测 3 次请求，其中两次含图，新增两条观测后为当前的 130 条。内容、压缩程度和 PNG/JPEG/WebP 格式变化未改变所测同尺寸图片的计数。

### Issue #7 预算算例

按反馈中的 430,066 个文本 token、49 个工具和 40 张 910 × 1287 图片，以 DeepSeek 的 1,048,576 窗口计算，文本与工具余量为 `1024 + 49 × 20 = 2004`。图片中心计数合计 28,600，图片软余量为 `40 × 8 = 320`。客户端若把输出上限设为整个窗口，适配后为 `1048576 - 430066 - 2004 - 28600 - 320 = 587586`。

该算例验证本地预算计算，没有重放原来的完整会话；实际图片用量仍取上游返回的 `usage`。

## 上游行为复测（2026-10-15）

通过直连接口向 `DeepSeek-V4.1-Flash` 和 `qwen3.8-27b` 发送 20 次合成请求，均关闭思考并要求只回复 `OK`。16 次成功，4 次故意设置过大输出预算的请求返回 HTTP 400，正文明确说明最大上下文长度和输入或输出超限，未出现“服务器繁忙”的含混报错。

| 场景 | 模型 | 上游输入 token | 发送的 `max_tokens` | 结果 |
|---|---|---:|---:|---|
| 短文本，输出设为整个窗口 | DeepSeek | 未返回 | 1,048,576 | HTTP 400，上下文超限 |
| 短文本，输出设为整个窗口 | Qwen | 未返回 | 262,144 | HTTP 400，上下文超限 |
| 7,184 token 文本，只扣除通用余量 | DeepSeek | 未返回 | 1,047,552 | HTTP 400，上下文超限 |
| 同一文本，扣除文本计数和通用余量 | DeepSeek | 7,184 | 1,040,368 | 成功 |
| 40 张 910 × 1287 图片，仅按文本适配输出预算 | DeepSeek | 28,652 | 1,047,540 | 成功 |
| 40 张 910 × 1287 图片，仅按文本适配输出预算 | Qwen | 44,900 | 261,105 | 成功 |

两模型的短文本、40 张图片请求，在输出上限为 8 或未指定时也均成功。上表列出部分对照；第四个预期 400 为 DeepSeek 单图请求将输出上限设为整个窗口。

这组结果确认上游在所测超限场景下能明确报错。40 图请求成功时，上游报告的输入与发送的输出上限之和超过模型窗口，但实际回复均只有 2 token。这只能证明短回复可以通过，不能保证同样预算下的长输出也能完成，也不能据此取消图片预算或认定上游从不校验图片上下文。当前仍使用图片软估计为输出保留空间。

这些图片是有效的合成 PNG，没有复现 Issue #7 原来的约 43 万 token 长会话。WebVPN 隧道遇到会话重定向，未完成同组验证。上游部署与校验行为可能变化，当前结果只描述上述请求。

| 请求 | 上游输入 token | 首字等待 | 结果 |
|---|---:|---:|---|
| 约 50 万 token 文本 | 511,999 | 59.4 秒 | 完整成功 |

通过修改后的代理重测，另一组 972,799 token 的请求在约 162.8 秒返回首字并正常结束；64 MiB 四图请求约 8.7 秒完成。

### 前缀缓存对照

同日用约 13 万 token 补测连续对话。首次请求未命中缓存，首字等待 11.7 秒；保留系统提示和原有历史，追加一轮追问后，131,079 个输入 token 中有 130,816 个命中缓存，首字等待降到 0.64 秒。再次发送相同请求时为 0.73 秒。

DeepSeek 请求的前缀可被上游缓存复用，代理保留这项行为。固定系统提示、工具定义和已有历史，把新问题追加在末尾，有助于复用缓存。缓存容量、保留时间与请求路由由上游决定；这组 13 万 token 的结果不能直接外推为 100 万 token 的等待时间。
