# 上游并发实测

2026-10-28 使用同一账号，经校园网直连学校 Chat Completions 接口测试。请求绕过本地代理，使用合成的短文本、流式响应和 256 token 输出上限；DeepSeek V4.1、Qwen 均关闭思考。每组并发发起，上一组结束后才开始下一组。成功表示完整收到 `[DONE]`，不只是收到 HTTP 200。

| 请求组合 | 发起数 | 完整成功 | 明确并发 429 |
|---|---:|---:|---:|
| DeepSeek V4.1 | 2 | 2 | 0 |
| DeepSeek V4.1，4 路首次测试 | 4 | 3 | 1 |
| DeepSeek V4.1，4 路复测 | 4 | 3 | 1 |
| DeepSeek V4.1，3 路复测 | 3 | 3 | 0 |
| Qwen | 3 | 3 | 0 |
| Qwen | 4 | 4 | 0 |
| DeepSeek V4.1 × 2 + Qwen × 2 | 4 | 4 | 0 |

两次并发拒绝均为真实 HTTP 429，JSON 错误码为 429，错误消息为“您的同时进行中的请求过多，请等待已有请求完成后再试”。拒绝在约 0.08–0.17 秒内返回，同组其余请求正常生成并结束。

另有一组 3 路 DeepSeek 请求在 60 秒内未收到响应头，测试主动中止；没有收到限流错误，不能将其计为并发拒绝，也不能确定是网络还是上游处理导致。该异常样本未纳入上表的有效边界观测。

这些结果支持当日所测 DeepSeek 账号存在 3 路并发边界。Qwen 测到 4 路成功后未继续增加，不能据此确定其上限。混合模型 4 路均被接受并完成，但生成阶段并未全部重叠，不能据此判断后端同时执行数，也不能认定所有模型共享同一个 3 路额度。

本次仅测试一个账号与校园网直连路径，没有确认不同账号、IP、WebVPN 或其他模型的计数规则。学校可能调整策略；短请求的成功也不保证长上下文、多图或长时间生成具有相同表现。

## 使用建议

- DeepSeek 客户端先使用 1–2 路并发，并把其他客户端、会话和网页中未结束的请求考虑在内。这里的 1–2 路是操作建议，并未在代理中新增限制。
- 收到明确的并发 429 后，等待已有请求完成，再采用逐步延长间隔的重试，避免多个请求立即同时重发。
- 代理保留上游 429；不会针对并发拒绝自动排队或重试。一般的“服务器繁忙”也可能来自参数或其他上游问题，不能仅凭这句话确定并发超限。
- 本地的 64 路保护上限和请求体总量预算独立于上游限制。提高本地容量不会增加学校配额。
